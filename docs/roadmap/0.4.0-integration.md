# `0.4.0` · Integration

**Status:** shipped · **Theme:** stop being a library you wire up by hand

> **Both items shipped.** This plan is kept as written, because what a plan got
> wrong is the useful part of it. Two things it got wrong, both recorded at the
> point they appear below:
>
> - The resumer could not "subscribe to `approval.resolved` across sessions" —
>   `MultiplayerBus` is keyed by session, and the bus is at-most-once, so a
>   subscriber would have needed the reconciling sweep behind it anyway. It
>   listens locally and reconciles from the store instead
>   ([ADR 0006](../decisions/0006-local-resume-not-bus.md)).
> - `runId` and `stepId` were not, as claimed, "exactly the keys this needs".
>   A run id has no registry key to look it up in; `workflowId` had to join them.
>
> The API precondition, on the other hand, held exactly: everything the research
> read on `1.65.0-alpha.7` behaves the same on published `1.64.0`.

Everything through `0.3.0` was about the package being *correct*: tested,
authorized, durable, distributed, operable. None of it made the package easier
to *reach*. Both remaining `Next` items are integration surfaces, and the
[research on Mastra's actual APIs](./research/2026-09-07-mastra-apis.md) changed
both plans — one grew, one shrank.

| Item | Was | Now | Why it moved |
| --- | --- | --- | --- |
| R6 · Workflow gates | `M` · high | `L` · high | It is a resumer, not a factory. The suspended run has to be woken. |
| R7 · Channel participants | `L` · medium | `M` · high | No vendor SDK. Adapters are Mastra's packages; this is a mapping. |

Ship R7 first. It is smaller, it is self-contained, and R6 benefits from having
a second real consumer of `Participant` before its shape is pinned by a workflow
API.

## R7 · Channel participants

### The problem

A session can already span a web UI and a Slack thread — `Participant.surface`
and `resourceId` exist for exactly that. Nothing populates them from a Mastra
channel, so every adopter writes the same twenty-line translation, differently.

### What the research changed

R7 sat at medium confidence on the premise that *each adapter drags in a vendor
SDK, which fights the zero-dependency rule and may belong in a companion
package*. **That premise was wrong.** Mastra's adapters are separate
`@chat-adapter/*` packages the host installs and hands to its own agent. This
package never imports one.

What remains is a pure mapping between two shapes we already own, testable with
a plain object.

### Shape

```ts
import { channelParticipant } from "@avant-garde-ai/mastra-multiplayer/channels";

const participant = channelParticipant({
  surface: "slack",
  actor: { userId: "U06CK1E9HN2", fullName: "Alice Chen" },
});
// { id: "slack:U06CK1E9HN2", displayName: "Alice Chen",
//   role: "editor", surface: "slack", resourceId: "slack:U06CK1E9HN2" }
```

Plus a session resolver, because mapping a channel thread to a session is the
host's decision — one session per thread, per channel, or per support ticket:

```ts
const bridge = channelBridge(multiplayer, {
  resolveSession: async ({ surface, threadId, channelId }) => sessionIdFor(threadId),
  role: ({ actor }) => (admins.has(actor.userId) ? "owner" : "editor"),
});

await bridge.receive({ surface: "slack", actor, threadId, channelId, text });
```

`receive` joins the participant if new, then calls `send`. That is the whole
integration.

### Decisions to make, not discover

- **Bots are excluded by default.** `actor.isBot` can be `'unknown'`. A bot
  posting into a shared session is a participant by every structural measure and
  not one by any useful one — it would appear in `rosterPrompt()` and count
  toward a quorum. Excluded unless `allowBots: true`, and documented rather than
  left to each adapter.
- **`id` is prefixed with the surface.** `slack:U06…` not `U06…`. Two platforms
  will eventually hand out the same opaque id, and a collision silently merges
  two people into one participant — which, with `excludeRequester`, silently
  breaks four-eyes.
- **Role is a function, not a field.** Who is an approver is the host's policy,
  and it is the one thing here that is security-relevant.

### Done when

- `channelParticipant` and `channelBridge` ship from
  `@avant-garde-ai/mastra-multiplayer/channels`, with no new dependency.
- Tests cover the mapping (including missing `fullName`, `isBot: 'unknown'`, and
  id collision across surfaces), joining once versus twice, and role resolution.
- An example under `examples/` shows a session spanning a web client and a Slack
  thread.
- `docs/CONCEPTS.md` stops saying `Participant.resourceId` "is not yet read by
  the library".

### Size

`M`. Two days, most of it tests and the example.

## R6 · Workflow-step approval gates

### The problem

[`examples/approval-gate/refund-tool-polling.ts`](../../examples/approval-gate/refund-tool-polling.ts)
polls the store in a loop, which burns a run for the duration and dies with the
process. Mastra has `suspend()`/`resume()` and a durable snapshot; this package
should use it.

### What the research changed

The roadmap called this "a factory wrapping `suspend()`/`resume()`", sized `M`.
Reading the API showed the factory is the easy half:

**Votes arrive over this package's HTTP surface. Workflows resume through
`run.resume()`.** Nothing connects them. A step that suspends and a vote that
resolves an approval are two halves of a bridge that does not exist — build only
the factory and every gate suspends for ever.

So R6 is two pieces, and the second is the real work.

### Piece 1 — the step

Mastra re-executes the step from the top on resume with `resumeData` populated,
which fits the gate model exactly:

```ts
const refundGate = approvalStep(multiplayer, {
  id: "refund-approval",
  toolName: "refund-order",
  policy: fourEyes(),
  summary: ({ inputData }) => `Refund $${inputData.amountCents / 100}`,
});
```

Internally: no `resumeData` → `approvals.request({ runId, stepId, … })` then
`suspend({ approvalId, summary, votesNeeded })`. With `resumeData` → check the
decision, `bail()` on denial, `assertBinding()` then return on approval.

**`bail()` is the denial path**, not an exception. A denied approval is a
completed run with a `success` status and the rest of the step skipped —
throwing would fight the framework.

**`assertBinding()` still runs on resume.** The suspend/resume round trip is
exactly the window argument binding exists to close, and the step's `inputData`
on resume is the arguments that will actually execute.

### Piece 2 — the resumer

```ts
const resumer = approvalResumer(multiplayer, mastra);
resumer.start();   // subscribes to approval.resolved across sessions
```

On `approval.resolved`, read `runId` / `stepId` off the request, look up the
run, and `run.resume({ step: stepId, resumeData: { decision } })`.

**`ApprovalRequest.runId` and `stepId` have existed since `0.1.0` and nothing
has ever used them.** They are exactly the keys this needs — the scaffold
anticipated it.

> **Wrong, and found on the first attempt to use them.** A run id is not enough
> to look a run up: that needs `mastra.getWorkflow(workflowId)` first. Shipped
> with `ApprovalRequest.workflowId` added alongside them. The scaffold
> anticipated two thirds of it.

Four things this has to get right, none of them obvious:

- **Resuming is not idempotent-safe by assumption.** Two instances both see
  `approval.resolved`; both call `resume`. Reuse the `TurnLease` — it is already
  a per-session mutex with ownership checks — rather than inventing a second
  locking mechanism.
- **A resume can fail.** The run may be gone, the process may have restarted
  before the workflow store caught up. Failing loudly beats a gate that resolved
  in the ledger and never resumed, which looks fine from the outside and is not.
- **`sweepExpired` resolves approvals too.** An expiry is a resolution and must
  resume the run the same way, or a timed-out gate hangs where a denied one does
  not.
- **The bus is at-most-once.** `approval.resolved` is not a durable queue. A
  resumer that was down when the event fired never sees it, so it needs a
  reconciling sweep on start: find approvals resolved with a `runId` whose run is
  still suspended, and resume them.

> **This point turned out to sink the bus entirely, not just supplement it.**
> If the sweep is the guarantee, the subscription is only a latency
> optimisation — and a per-session bus cannot deliver "every resolution
> anywhere" without new surface on both implementations. So the optimisation is
> a local `ApprovalGate.onResolved` hook, which is free, and the sweep is the
> correctness. [ADR 0006](../decisions/0006-local-resume-not-bus.md).
>
> The sweep also needed `ApprovalRequest.resumedAt` to stay affordable: without
> it, every approval ever resolved is re-checked on every sweep, for ever.

### Done when

- `approvalStep` and `approvalResumer` ship from
  `@avant-garde-ai/mastra-multiplayer/workflows`, with `@mastra/core` still an
  optional peer and the workflow types declared structurally, as in
  [ADR 0004](../decisions/0004-structural-mastra-types.md).
- Tests cover: suspend on first execute, approve → resume → binding re-checked,
  deny → `bail`, expiry → resume, a double resume across two instances resolving
  once, and the start-up reconciliation.
- `examples/approval-gate/refund-tool.ts` is rewritten without the polling loop,
  and the polling version is kept alongside as the no-workflows path.
- `docs/APPROVALS.md`'s "Waiting for a decision" section stops calling option 3
  aspirational.

### Size

`L`. The step is a day. The resumer, its concurrency, and the reconciliation are
the rest.

### Before starting

**Re-check the API against the published `@mastra/core`, not `main`.** The
research read `1.65.0-alpha.7` from the monorepo — a working version, not a
release. This package's peer range is `>=1.0.0`, and building against something
that only exists on `main` would break every consumer.

If `run.resume({ step, resumeData })` differs in the published release, Piece 1
is unaffected (the step shape is stable and old) and Piece 2 needs rework.

## Not in this milestone

- **R14's lease covering workflow resumes** — noted above as reuse, not new
  work. If it turns out a workflow resume needs different semantics from a turn,
  that is a finding, and it gets its own item rather than quietly widening
  `TurnLease`.
- **A UI for approvals.** Still deliberately absent
  ([roadmap](../ROADMAP.md#deliberately-not-doing)). The headless hook plus
  `evaluate()` on the client is enough to render a gate; a vendored design
  system is not.
- **Anything from [Horizons](./HORIZONS.md).** Co-editing and the evaluation
  harness stay research until someone asks with a real use case attached.

```
R7 (M) ──▶ R6 piece 1 (S) ──▶ R6 piece 2 (M) ──▶ 0.4.0

```

API check goes badly. That is the point of ordering it first.
